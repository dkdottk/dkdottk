# Spec-Driven Development

В этом проекте работаем по **Spec-Driven Development (SDD)** / Spec-Driven Design.

## Идея

Сначала фиксируем **спецификацию** (что и зачем строим), затем план, затем код и проверки. Код — следствие spec, а не наоборот.

## Цикл

1. **Intent** — цель, пользователь, границы.
2. **Spec** — поведение, сценарии, данные/API, ограничения, edge cases, критерии приёмки.
3. **Plan** — шаги реализации, затрагиваемые файлы, риски.
4. **Implement** — код строго по approved spec.
5. **Verify** — тесты и ручные проверки против acceptance criteria.

Изменение поведения = сначала правка `spec.md`, потом код.

## Структура

```text
specs/
  <feature-name>/
    spec.md      # источник истины по поведению
    plan.md      # как реализуем
    notes.md     # опционально: вопросы и решения
docs/
  spec-driven-development.md
AGENTS.md        # обязательные правила для агентов
```

## Что должно быть в `spec.md`

- Цель и контекст
- In scope / Out of scope
- Поведение (сценарии или требования)
- Ограничения (безопасность, perf, совместимость)
- Acceptance criteria (проверяемый чеклист)
- Открытые вопросы (если есть)

## Что не делаем

- Не кодим «на глаз» без spec для новой фичи или изменения поведения
- Не расширяем scope молча — только через обновление spec
- Не считаем чат источником истины после того, как spec утверждён
